📐 4-Step HLD System Design Framework Interactive Module

System Design interviews at product-based companies measure how structured and methodology-driven you are. Use the 4-step framework below alongside the live interactive capacity estimation calculator to master system sizing.

1. Requirement Clarification (Functional & Non-Functional)
Define boundaries. Establish primary user workflows (FRs) and quality constraints (NFRs: Availability SLA, Read/Write ratio, Latency budget $p99 < 50\text{ms}$).
2. Back-of-the-Envelope Capacity Calculations
Convert user traffic into QPS, peak QPS, ingress/egress bandwidth, storage over 5 years, and cache memory required (Pareto 80/20 rule).
3. High-Level Architecture & API Specs
Draw microservices, load balancers, database choices (SQL vs NoSQL), message brokers, and draft core REST/gRPC endpoint signatures.
4. Deep Dive & Bottleneck Mitigation
Address single points of failure (SPOF), caching eviction policies, DB sharding strategy, circuit breakers, and rate limiting algorithms.

💡 Step-by-Step Calculation Breakdown & Formulas

1. QPS (Queries Per Second) Formula
Average QPS = (DAU × Writes/Day) ÷ 86,400 seconds
Why 86,400? There are 24 hours × 60 mins × 60 secs = 86,400 seconds in a day. Peak QPS is estimated at 2x to 3x average QPS to handle traffic surges.
2. Read-to-Write Ratio Impact
Read QPS = Write QPS × Read Ratio
Consumer web applications (Twitter, YouTube, News feeds) are heavily read-heavy ($100:1$). Write-heavy applications (IoT logging, metric streams) have low ratios ($1:1$).
3. Storage Growth Math
Daily Storage = Total Writes × Payload Bytes
5-Year Storage = Daily Storage × 365 days × 5 years
Converting bytes to GB/TB: divide bytes by $1024^3$ for GB and $1024^4$ for TB.
4. Pareto 80/20 RAM Cache Rule
RAM Cache = 20% × Daily Read Requests × Payload Bytes
The Pareto Principle states that $20\%$ of hot content drives $80\%$ of total user views. Caching this $20\%$ hot set in Redis handles $80\%$ of reads without hitting database disks.
