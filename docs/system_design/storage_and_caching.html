1. Storage Engine Fundamentals & Mechanical Sympathy

Storage engines define how databases read from and write to disk/SSD. The fundamental trade-off is between Sequential I/O (LSM-Trees) for extreme write throughput and In-Place Updates (B+Trees) for low-latency point/range reads.

Dimension LSM-Trees (Log-Structured Merge-Tree) B+Trees (Clustered Index Pages)
Primary Database Mapping RocksDB, Apache Cassandra, Google Bigtable, ScyllaDB, DynamoDB (Storage Nodes) PostgreSQL, MySQL InnoDB, SQL Server, Oracle, SQLite
Write Path Mechanism Append-only sequentially to WAL + In-Memory MemTable (SkipList). Never modifies on-disk files in-place. In-place update of 8KB/16KB disk pages + WAL / Redo Log for crash recovery. Requires page-level latching.
Write Amplification (WA) Moderate to High during Compaction ($\approx 10\times - 30\times$), but disk writes are strictly sequential (fast on NVMe/SSD). High random write overhead; updating 1 byte requires dirtying and flushing an entire 8KB/16KB page to disk.
Read Path Mechanism MemTable $\rightarrow$ Bloom Filter $\rightarrow$ Block Cache $\rightarrow$ SSTable binary search $\rightarrow$ Merging multiple versions. Direct root-to-leaf traversal ($O(\log_B N)$ page reads). Deterministic, single-page point read latency.
Compaction Strategy Size-Tiered (optimized for writes) vs Leveled Compaction (optimized for reads and low space amplification). Vacuuming / Page splitting / B-Tree rebalancing during page fill factor saturation.

🌿 LSM-Tree Write & Read Architecture

1. Write: Appends to Write-Ahead Log (WAL) for durability, then inserts into an in-memory sorted MemTable.
2. Flush: When MemTable exceeds threshold (e.g., 64MB), it becomes immutable and is flushed to disk as a sorted string table (SSTable).
3. Compaction: Background workers merge overlapping SSTables, purging deleted tombstones and keeping only newest key versions.

📑 B+Tree Page Balancing & Latches

1. Tree Structure: Root node $\rightarrow$ Internal nodes (Routing pointers) $\rightarrow$ Leaf nodes containing full records linked sequentially.
2. Concurrency: Requires Reader/Writer page latches (Lock coupling / latch crabbing) which can become lock bottlenecks under high concurrent writes.
3. Best For: Heavy point queries and range scans where predictable $<2\text{ms}$ $p99$ latency is strictly required.

2. Distributed Cache Anomalies & Production Mitigations

When scaling caches (Redis/Memcached) under millions of QPS, three major anomalies can bring down upstream databases. Here is how Staff Engineers mitigate them.

Cache Anomaly Failure Root Cause Production Mitigation Strategy
1. Cache Stampede (Thundering Herd) A high-traffic "hot key" expires in Redis. Thousands of concurrent requests experience a cache miss simultaneously and hammer the primary DB. • Singleflight / Distributed Mutex: Only 1 request acquires a lock to recompute and populate the cache; other 9,999 requests wait for the result.
• XFetch Probabilistic Early Expiration: Asynchronously refreshes cache before expiration when $\Delta \cdot \beta \cdot \ln(\text{rand}()) > \text{TTL}$.
2. Cache Penetration Malicious clients or bad actors query non-existent keys (e.g., `user_id=-999999`) that bypass cache and repeatedly hit DB. • Bloom Filter at Edge/Gateway: Fast-rejects non-existent keys before touching Redis or DB.
• Null Object Caching: Cache empty results (`{ "found": false }`) with a short 60s TTL.
3. Cache Avalanche Massive batch of cache keys created at the same time (e.g., midnight batch job) expire at the exact same second, dumping all read traffic on DB. • TTL Jitter / Entropy: Add random deviation to expiration: $\text{TTL} = \text{Base} + \text{Random}(0, \text{Jitter})$.
• Multi-level Caching: Local in-memory L1 cache (Caffeine/MemoryCache) backed by distributed L2 Redis cluster.

🛡️ Production Code Snippet: .NET Singleflight Stampede Protection

public async Task<ProductDto> GetProductWithSingleflightAsync(string productId)
{
    var cacheKey = $"prod:{productId}";
    var cached = await _redis.GetStringAsync(cacheKey);
    if (cached != null) return JsonSerializer.Deserialize<ProductDto>(cached);

    // SemaphoreSlim keyed per product to prevent Thundering Herd
    var keyLock = _locks.GetOrAdd(productId, _ => new SemaphoreSlim(1, 1));
    await keyLock.WaitAsync();
    try
    {
        // Double-check cache inside lock
        cached = await _redis.GetStringAsync(cacheKey);
        if (cached != null) return JsonSerializer.Deserialize<ProductDto>(cached);

        var product = await _db.Products.FindAsync(productId);
        var jitterSeconds = Random.Shared.Next(30, 90);
        await _redis.SetStringAsync(cacheKey, JsonSerializer.Serialize(product), 
            new DistributedCacheEntryOptions { AbsoluteExpirationRelativeToNow = TimeSpan.FromMinutes(10) + TimeSpan.FromSeconds(jitterSeconds) });
        return product;
    }
    finally
    {
        keyLock.Release();
    }
}
