1. Consensus Protocols & Tunable Quorum Consistency

In distributed systems, machines must agree on state transitions despite packet drops, network partitions, and machine crashes.

Protocol / Model Core Mechanism Guarantees & Trade-offs Enterprise Examples
Raft Consensus Leader-driven with strict term epochs, randomized election timeouts ($150\text{ms}-300\text{ms}$), and two-phase log commit. Guarantees Linearizability and strict CP (Consistency/Partition tolerance). Requires majority $\lfloor N/2 \rfloor + 1$ nodes active. etcd (Kubernetes metadata), HashiCorp Consul, CockroachDB, TiKV
Dynamo-style Quorum ($N, R, W$) Peer-to-peer replication across $N$ nodes. Writes succeed when acknowledged by $W$ nodes; reads poll $R$ nodes. • Strong Consistency when $R + W > N$ (Guarantees at least 1 overlapping replica with latest version).
• Eventual Consistency when $R + W \le N$ (Low latency, high availability, risk of stale reads). 		Apache Cassandra, Amazon DynamoDB, ScyllaDB, Riak
Vector Clocks vs LWW Vector clocks track causality across distributed nodes: $V(A) < V(B)$. Last-Write-Wins (LWW) relies on physical NTP timestamps. Vector clocks detect true concurrent conflicts but incur metadata growth. LWW is simple but silently overwrites data due to clock skew/drift. DynamoDB (Version attributes), Cassandra (LWW column timestamps)

💡 The Quorum Overlap Principle (Pigeonhole Theorem)

If a cluster has $N = 5$ replicas, and we set $W = 3$ (write to 3 nodes) and $R = 3$ (read from 3 nodes), then $R + W = 6 > 5$.
By the Pigeonhole Principle, at least $1$ node in any read quorum must have participated in the latest write quorum. Comparing record version timestamps resolves the latest true state.

🔧 Background Entropy Resolution (Merkle Trees)

• Read Repair: When a read quorum encounters a stale node, it asynchronously pushes the newest version back to that stale node.
• Anti-Entropy (Merkle Trees): Replicas build hierarchical hash trees of key ranges. During background sync, nodes only compare sub-tree hashes, transferring only divergent data over the network.

2. Distributed Locks, Fencing Tokens & Dual-Write Mitigation

Preventing race conditions and dual-write data inconsistencies across independent microservices and databases.

🚨 The Martin Kleppmann Fencing Token Dilemma

A client acquires a distributed lock (e.g., Redis Redlock) with a 10-second TTL. Suddenly, the client experiences a 15-second Stop-The-World (STW) Garbage Collection pause. The lock expires, and Client B acquires it. Client A wakes up, unaware its lock expired, and writes corrupting data to storage.

Solution: Monotonically Increasing Fencing Tokens
Lock Service returns token #33 ➔ Storage layer checks UPDATE data SET val = 'x', token = 33 WHERE token < 33;
When delayed Client A tries writing with stale token #32, the storage layer rejects it immediately.
Pattern Problem Solved How It Works
Transactional Outbox + CDC Dual-write hazard: Writing to DB and publishing to Kafka in a single request cannot be atomic without 2PC. Write business data and an outbox_event in the same local DB ACID transaction. A CDC connector (Debezium) tails DB WAL / transaction log and streams to Kafka.
Orchestrated Saga Distributed transactions across multiple microservices with complex compensation logic. A centralized Saga Orchestrator state machine coordinates service steps via command queues and triggers backward compensating transactions on step failure.
Choreographed Saga Distributed transaction coordination without a single orchestrator bottleneck. Services listen to domain events and reactively execute local transactions and emit follow-up events. Best for simple 2-3 step flows; difficult to debug for large topologies.
